# Worlds product brief

Worlds turns a person's actual agent setup into a place where people and agents can work together. It is a spatial workspace, with useful tasks and outputs behind the characters and objects. A beautiful world that cannot explain real work does not satisfy the product.

## Primary loop

Connect a source → discover a permitted roster → review an AgentPlan → review a WorldPlan → build a validated scene → enter, inspect work, collaborate, and return.

The source decides which agents exist. The user and planner decide where they belong. A theme changes the environment, not identity or permissions. Suggested agents remain uncreated recommendations until separately provisioned through a supported provider path.

## First user and first useful moment

A builder, designer, marketer, or small team already uses agents and wants to understand what they are doing together. The first useful moment is finding the right agent, seeing its current work and source freshness, and opening an actual output or supported continuation link.

## World as interface

Rooms represent projects or work areas. Desks and workshops are interaction targets. A library contains permitted artifacts. A project board shows tasks, blockers, and history. People and agents are recognisable at map scale. An inspector contains normal readable controls. A direct list provides the same important actions without walking.

World templates: Office and Café are familiar starting points; Village is the signature playful world; Cyberpunk is the expressive alternate. The full map has districts, paths, landmarks, and shared space. Start with a playable section and a consistent camera/asset style.

## Scope

Initial 20–30-hour local alpha: one polished world, source-driven plans, labelled sample mode, one verified source discovery path where available, one real MCP update, useful inspection, persistence, and two local clients with shared presence. This is a target to validate, not an assertion that every integration is achievable in that time.

Expanded design system, several production-quality world kits, comprehensive rig/animation libraries, public hosted multiplayer, commerce, and community marketplace require further milestones. Paid templates, voice/video, infinite terrain, combat, and autonomous agent provisioning are outside the first alpha.

## Integration boundaries

Nebula is the first intended agent source/runtime. Its documented CLI is a discovery route to test. The Worlds MCP server lets a permitted agent update Worlds; it does not automatically grant Worlds access to Nebula's roster. GitHub provides reviewed definitions or versioned world packs, not automatic runtime telemetry. Shared Nebula channels do not replace game networking.

Only show capabilities verified in the current installation. If task dispatch is unsupported, use a verified continuation link. Never make a sample conversation look like a live agent response.

## Source and state contracts

SourceSnapshot: stable source/workspace/entity IDs, observed metadata, relationships, scope, timestamp, provenance.

AgentPlan: selected existing agents, visual aliases, appearances, assignments, relationship rationale, separate proposed additions.

WorldPlan: theme, zones, paths, stations, spawns, actor bindings, capacities, allowed assets, revision, change summary.

BuildManifest: the exact reviewed plan revision and validated resolved assets rendered by the engine.

Run state and network freshness are separate. Agent-reported completion is not human acceptance. Silence is not success. Source refresh creates a diff rather than discarding custom layouts.

## Success evidence

Two different rosters generate different worlds without source-code changes. Renaming an agent preserves identity. A permitted user can inspect real work. Two clients can join, move, and reconnect. Unreviewed plans and unauthorized actions are rejected. A clean local install works. Public claims match the tested feature matrix.
