# Worlds design-system brief

Match the depth and discipline of the authorised Glob system. Build an original Worlds identity. Audit first; do not guess what Glob contains.

## Read-only Glob audit

Inventory brand tokens, components, OS/workspace patterns, landing pages, design explorer, mascot geometry and poses, 3D rigs, materials, cameras, lighting, motion, videos, content templates, export conventions, asset manifests, and validation. Distinguish production, experiments, fixtures, proposed work, generated renders, and real meshes/rigs. Cite paths and explain reuse rights.

Produce a coverage matrix: Glob capability → evidence → Worlds equivalent → reuse/adapt/rebuild → priority → acceptance proof. Exclude secrets and private operational data. Transfer mechanics with permission; create original character identities and art. If the Glob checkout is unavailable, explicitly mark the audit pending and build an independent baseline rather than inventing findings.

## Brand foundation

- White background is the primary launch identity. Charcoal text, restrained borders, generous whitespace, and a few bright accents.
- Gather informs spatial clarity; Grok Bot informs recognisable agent personality; Nebula informs simple multiplayer product language. None supplies assets or endorsement.
- The landing page should feel like a focused modern startup launch. Show the product immediately and explain it plainly.
- Put intense colour, fantasy, environmental storytelling, and arcade character in world canvases. Do not spread neon chrome across forms and navigation.
- Separate brand accent, semantic status colour, character palette, and world theme tokens. The same actor keeps identity when changing worlds.

## System layers

1. Foundations: colour roles, type scale, spacing, grid, radii, elevations, focus, density, breakpoints, icon sizes, motion timing, reduced motion, accessible contrast.
2. Primitives: buttons, inputs, selects, checkboxes, tabs, badges, tooltips, dialogs, sheets, toasts, menus, skeletons, empty/error states.
3. Product patterns: source connection, roster selection, entity row, provenance label, agent card, plan diff, review/approval, world preview, task inspector, artifact tile, avatar stack, invite/session state, activity feed.
4. Spatial language: floor grid, zones, workstations, paths, landmarks, camera limits, collisions, selection/hover, labels, minimap only if useful, world/list parity.
5. Characters and motion: original silhouettes, scale rules, human/agent indicators, palette, props, expressions, pose/animation library and exports.
6. Communication: world cards, feature illustration, screenshot frame, documentation diagrams, demo title/end cards, social-safe visual crops. No invented testimonials or usage metrics.

## Mascot and character production

Develop a small original family with distinctive silhouettes: for example a visor-based courier, an angular archivist, and a hooded maker. These are appearance options, not hardcoded agent jobs. Keep human avatars readable and different from agent indicators. Avoid undifferentiated glossy blobs.

Deliver concept sheet, proportions, front/side/back or turntable references, colour/material variants, accessory attachment rules, and map-scale readability checks. For actual 3D assets, deliver geometry, material setup, rig/bones if used, reusable pose definitions, animation clips, export settings, bounding box/origin conventions, thumbnails and performance budget. Mark procedural non-rigged assets accurately.

Required state library: idle, walk, working, reading/thinking, wave, presenting/handoff, needs-input, success, failed, offline. Match state to actual data; animation remains deterministic and cosmetic. Pose renders alone do not satisfy a request for rigs or animations.

## Design-system explorer

Create a local /design route with tokens, component states, product patterns, character turntables/pose controls, material/lighting tests, world tiles, responsive examples and accessibility notes. Every live example should use the real shared component or asset definition. Show asset provenance and whether an item is working, placeholder, concept, or planned.

Start with a small complete system supporting the alpha. Expand coverage after the first working loop. Do not spend the full sprint building an elaborate style guide around a nonfunctional product.

## Landing and worlds explorer

Local routes: / for landing, /worlds for the large theme explorer, /onboarding for source/plan setup, /workspace/:id for the product, /design for the system.

Landing structure: concise value proposition and product view; a substantial world gallery; how connect/plan/build works; human-and-agent interactions; open-source/remix explanation; real integration status; local demo entry. Link only implemented destinations. No fake customer logos, install counts, waitlist submissions, pricing, or live-site claims.

The worlds section is a major product surface, not four small decorative cards. Offer large previews, theme/setting filters, detail views, stations/area layout, solo/shared suitability, tested-versus-concept labels, and “Try locally” only where it works. Use the same agent roster when comparing themes. Ensure each preview clearly states whether it is raster art or the real renderer.
